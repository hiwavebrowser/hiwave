## Problem (Trace #243)

`b11_settings_save` finds the sidebar's Settings item with `hwdrive find`,
an Accessibility lookup written for the WebKit chrome. The RustKit chrome
(the default since #939) exposes no AX tree until A8, so the lookup finds
nothing and "the sidebar shows a Settings item" FAILs on every run. The
FAIL is honest; a4_settings covers the same flow (22/22). The row asks to
keep it failing and label it, so a batch reader does not take it for a
regression.

## Fix

- `KNOWN_GAPS` in driver.py maps `(check, assertion)` to `(gap, why)`. One
  entry: b11's "the sidebar shows a Settings item" → A8.
- `note()` labels a FAIL of a listed assertion when the app runs the
  RustKit chrome (`HIWAVE_RUSTKIT_CHROME` is not `0` in the app's env or
  the runner's). The detail starts `A8-blocked (the RustKit chrome exposes
  no Accessibility tree)`. Status stays FAIL, and the exit code stays 1.
- A PASS of a listed assertion says `known A8 gap passed: drop its
  KNOWN_GAPS entry`, so the label does not outlive A8.
- `result.json`: every assertion row has `blocked_by` (`"A8"` or `null`).
  `tally.blocked` counts labelled fails per gap, and they are still inside
  `tally.FAIL`. The summary line reads `PASS n  FAIL 3 (1 A8-blocked)  NOT RUN m`.
- Result rows are now 5-tuples, including the HID-safety stop row.
  `summarise()` is split out of `run()` so it can be tested.
- The README Results section describes the label.
- No reader of `result.json`'s tally exists in hiwave-macos, the umbrella
  hub, `~/.claude/hooks` or the lane scripts, so the new key moves nothing.
