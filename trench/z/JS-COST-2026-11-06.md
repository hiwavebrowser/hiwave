# JS cost after #891: S14 / S15 / S16 measurement (2026-11-06)

Measurement only. No code changes and no PR. Input to the "stay on Boa or switch engines" decision.

**Sources.** The batch 31 A/B logs in `batch31/x-batch31/`: index 0 and 2 are cand30 (develop before #891), index 1 and 3 are cand31 (after #891). Runs used 1280x800 and the default **5 s script budget**. Means below are over two runs per arm. I made no live loads.

**Reddit is replaced by lyft.** Reddit's capture is a challenge page: 1 script record, 0 ms of script (T17 territory). Lyft has the next-heaviest script load (9.2 s hold script_ms). Lyft's cand31 run 1 failed in 0.3 s, so its cand31 column comes from run 3 alone.

**No saved pages exist for these sites, so the real heavy modules could not be replayed.** T16 (`--save-html`) is unmerged. It also saves the settled DOM, not the scripts, and `--html-file` runs only inline classic scripts. For Q2 I therefore profiled **local proxy workloads** (real libraries from `~/Repos/openclaw/node_modules`, inlined) through the real embedding (`parity-capture --html-file --run-inline-scripts`):

| proxy page | contents | site it stands in for |
|---|---|---|
| `react-N` | React 19.2 prod. It renders 600 cards (about 9,000 DOM nodes) N times with `flushSync`. | github landing-pages (React) and lyft (Next.js) |
| `react-forced-N` | The same, plus one `offsetHeight` read per render | S16 |
| `marked-N` | marked parses a 53 KB markdown document N times | string- and regex-heavy code |
| `parse` | react-dom-client dev, 1.07 MB, top level only | parse and compile throughput |

I compared the same pages in pinned headless Chrome for Testing 148, both default and with `--js-flags=--jitless`.

**Instrumentation.** I applied a local patch in the js-measure checkout and never committed it. The diff is `js-measure/jsmeasure.diff`. It splits the classic `context.eval` into `Script::parse`, then `codeblock` (compile), then `evaluate`. It also times `Module::parse`, `link` and `evaluate`, and the embedder's own prelude evals. Every timing goes to stderr as a `JSMEASURE …` line. The build used `cargo-serial build --profile parity -p parity-capture`. I used the `parity` profile rather than `--release` because release has `strip = true`, and `sample` needs symbols. Both profiles are opt-level 3; parity drops LTO.

## Q3: S16, forced layouts inside script tasks (cand31)

| site | forced layouts | total ms | ms each | share of the 5 s budget | share of script task wall | top causes (`write:read`) |
|---|---|---|---|---|---|---|
| microsoft | **178** | **2,373** | 13 | **47%** | 36% | insert:computed_style 125, attribute:computed_style 46, insert:offset 2, attribute:scroll_size 2, shadow:computed_style 1 |
| github | 6 | 1,575 | **262** | 31% | 29% | insert:computed_style 2, form:element_scroll 1, attribute:rect 1, text:rect 1 (and text:computed_style 1) |
| apple | 19.5 | 359 | 18 | 7% | 32% | class:offset 4, attribute:computed_style 3, style:rect 3, style:offset 2, style:computed_style 2 |
| lyft | 3 | 82 | 27 | 2% | 1% (of hold) | text:rect 1, insert:rect 1, insert:scroll_size 1 |

**The budget clock charges forced layouts in full.** `with_script_js` (lib.rs ~2030) charges the wall time of the execution body against the 5 s budget. Forced layouts run inside that body. On microsoft, **47% of the budget goes to layout, not JavaScript**, and 217 module tags are then skipped as over-budget. **96%** of microsoft's forced layouts (171 of 178) are `getComputedStyle` reads after an insert or attribute write. Those reads need style, not boxes. Each costs a box-tree build: the hold's `build_ms` rose 1,421 → 2,280 when #891 let more modules run.

**#891 doubled microsoft's forced layouts**, from 92 / 1,386 ms (cand30) to 178 / 2,373 ms. More of the page's components now get to run inside the budget.

github's forced layouts are few but each one is a full-page layout of about 260 ms. In the proxy, a forced layout of a 9k-node tree costs 130 ms against Chrome's 7.7 ms.

## Three biggest costs and why they happen

1. **Boa's execution speed: 55–90% of script time on every site.** On the proxy it is 18× slower than V8's interpreter alone and about 100× slower than V8. Where the time goes:
   - GC and refcounting (34%): every value drop and clone touches the `Gc` header refcount, and mark/trace runs often.
   - Property lookup (22%): shape lookups, `PropertyMap` hashing, `for-in`.
   - Plain dispatch overhead (22%): register moves and the `run` loop.
   - Thread-local access (`_tlv_get_addr`, 3%) on every call.

   This is Boa's interpreter design, not our use of it. Host DOM calls are under 1% of samples. Per-site share of script time:

   | site | interpreter time after removing forced layouts and estimated parse | share of script time |
   |---|---|---|
   | github | ~3.6 s | ~65% |
   | microsoft | ~3.6–3.9 s | ~55–60% |
   | apple | ~0.6–0.8 s | ~60% |
   | lyft | ~8.2 s | ~90% |

2. **Forced layouts charged to script: 29–47% of the budget on microsoft and github.** Two mechanisms:
   - A `getComputedStyle` read after a DOM write forces a full box-tree build and layout, when it needs only style. That is 125 + 46 + 1 of microsoft's 178.
   - Each forced layout is non-incremental: about 260 ms each on github's page, and 130 ms on a 9k-node tree against 7.7 ms in Chrome.

   The budget clock counts all of it as JavaScript (S16).

3. **Parse and compile with no cache: about 10% of script time, paid on every load.** At ~139 ms/MB this is ~0.39 s for github, 0.4–0.7 s for microsoft and ~0.97 s for lyft. The 364 KB embedder prelude adds about 50 ms per load. Boa parses eagerly and compiles everything up front; there is no lazy function compilation or bytecode reuse. The bytes are fetched, parsed and compiled again on every load.

**Risk: regex.** It is not measurable per site without the sources. On string-heavy code, Boa's `regress` backtracker took 83% of the time, 71× slower than V8's interpreter-mode irregexp. Any site that tokenises or sanitises with regexes, such as markdown, templates or consent SDKs, will hit it.

## Embedding-level fixes, ranked by expected win

| # | fix | expected win | evidence |
|---|---|---|---|
| 1 | **Style-only `getComputedStyle`** (LAT7b) plus **forced-layout avoidance** for computed-style reads | microsoft: up to about −2.2 s per load (171 of 178 forced layouts need style only; 2.37 s total). github: about −0.5 s (2–3 of 6). apple: about −0.1 s | Q3 cause counts |
| 2 | **S16 policy: stop charging forced-layout time to the script budget** (pause the `with_script_js` clock across forced layouts) | Makes no page faster. Microsoft gets about 47% more JavaScript inside 5 s, so fewer of the 217 tags are skipped and more custom elements get defined. Pete's call (S16). | Q3, `with_script_js` |
| 3 | **Incremental/partial forced layout** (LAT11) | github: up to −1.3 s (6 forced layouts × 262 ms). Chrome does the same proxy read in 7.7 ms against our 130 ms. | Q3 and the proxy |
| 4 | **Boa GC tuning in our vendored fork** (collection threshold and heap growth) | Up to about 10–15% of execution. `Collector::collect` is 15.9% inclusive on react. Cheap to try; it is a vendored-crate knob. | Q2 |
| 5 | **Bytecode/compile cache** keyed by URL and content hash, plus a pre-compiled embedder prelude | Repeat loads only: −0.16 s (apple) to −0.97 s (lyft), plus about 50 ms on every load for the prelude. The parse half needs Boa's AST and bytecode to be serializable; Boa 0.22 has no such API, so this is fork work. | Q1 parse rate |
| 6 | **Time-slice long evaluations** with Boa's `evaluate_async_with_budget` (yields every N VM cycles), so the page thread can serve input mid-module | The total stays the same. The longest turn drops from 1.0–3.8 s to about one budget slice: a latency and input-responsiveness win (S23, LAT), not a load-time win. | Q1 longest turn |
| 7 | **Parse off-thread** | Moves about 10% (≈0.4–1 s) off the page thread on first load. Hard: `Script::parse` and `Module::parse` need `&mut Context` (the interner), so a second interner or context plus a merge is needed. | Q1 |
| 8 | **Binding fast paths** | Under 1%. Host calls are 0.8% inclusive of the React render. | Q2 |

## Interpreter speed versus our embedding, stated plainly

**What the embedding fixes can buy.** With #1–#3 and #5, the load-phase script time falls by about 2.5 s on microsoft, ~1.5–2 s on github, ~0.3 s on apple and ~1 s on lyft (repeat loads). That leaves roughly 3.5 s of pure Boa execution on github and microsoft and ~8 s on lyft.

**What it cannot buy.** On the proxy, Boa is **17.7× slower than V8 with the JIT disabled** and ~100× slower than V8. Those gaps are all in the interpreter (GC/refcount, shape lookup, dispatch, regex), and no embedding change moves them.

**Order of work.** The embedding fixes are the cheaper first step and they also address forced layout. That is an engine problem we keep whatever JS engine we use; it measured 17× slower than Chrome on the same tree. After them, interpreter speed is the large majority of what remains on every site.

**The decision question for Pete.** Can ~3.5 s (github, microsoft) or ~8 s (lyft) of JS per heavy-page load be accepted? If not, no Boa tuning short of a rewrite closes an 18× gap to an interpreter-only engine.

**Follow-ups before the decision, all no-live-load:**
1. Land T16 and add script-body saving, so the real ui-shell, landing-pages and `_app` bodies can be profiled instead of proxies.
2. Run the same proxy pages through QuickJS or another embeddable interpreter for an interpreter-to-interpreter comparison that does not assume a full V8 or JSC embed.
3. Dev-tools: log inserted-script and fetch-callback turns per source (lyft's 6.4 s is unattributed), and promote the module wave/import count to `info`.
