## The four fronts, honestly

### 1. Refactoring / speed (engine architecture)
Landed this week: paint-only animation frames (LAT2), hover restyle without relayout (LAT3),
scoped `:has()` (LAT6), SVG `<use>` index (LAT4b), stylesheet cache (LAT4), clean-tree reads
(LAT7, batch 30), chrome relayouts 202 → 7 per load (A10, #955), snapshot 28.8 → 1.5 ms per
turn (LAT8, #957). Every one of these is a *skip*: avoid the full rebuild when nothing changed.

The ceiling is still: **every relayout is a whole-document rebuild** (style, layout, display
list). The remaining wins are architectural:
- **LAT11 incremental build + partial layout** — restyle/relayout only the dirtied subtree.
  This is what makes timer-driven and hover-driven churn cheap instead of avoided.
  **Measured 19:40:** a forced layout on microsoft is 93 % style build (2,294 ms over 174
  forced layouts) and 7 % layout; a style-only `getComputedStyle` path (LAT7b) therefore
  saves ~170 ms, not 2.2 s. The first LAT11 slice is incremental RESTYLE, and it is where
  the JavaScript measurement's biggest win actually lives.
- **B15 absolutely-positioned containing block** — we use the DOM parent, Chromium the
  nearest positioned ancestor. Fundamental; blocks C15, C15b, B13b, #935 and most abspos
  diffs on sites.
- LAT7b (`getComputedStyle` forces layout for non-layout props), LAT7c (WAAPI writes force
  layout), LAT9 (per-image budget), LAT5 (pointer policy, Pete), LAT10 (script-turn cap, Pete).

### 2. Animation

### 3. JavaScript
The least-worked front and the long pole on heavy sites. Boa 0.22, no JIT. Measured:
microsoft's 31 modules + 87 imports cost ~17 s of JS (S14); import graphs fetched one hop at a
time (S15, #891 open); forced layouts inside scripts charged to the budget (S16); a reddit
load held the page thread 11 s (S23); github's bundle throws at `getPropertyValue` (S24).
Nothing in this list has a PR except #891.

**Measured 11-06 18:24 (`JS-COST-2026-11-06.md`, batch-31 captures after #891, no live
loads):**

| site | script time | longest turn | forced layouts inside script | est. parse+compile |
|---|---|---|---|---|
| microsoft | 4.35 s | 1.29 s | 2.37 s (171 of 178 are style-only `getComputedStyle` reads) | 0.4–0.7 s |
| github | 4.03 s | 1.04 s | 1.58 s (one forced layout ≈ 260 ms) | ~0.39 s |
| lyft | 9.25 s | 3.8 s | — | ~0.97 s |
| apple | 1.24 s | — | 0.36 s | ~0.16 s |

#891 cut idle network inside the script phase on microsoft 1,515 → 0.3 ms and github
2,014 → 189 ms. Boa's profile on a React stand-in: GC/allocation 34 %, property lookup 22 %,
interpreter loop 22 %, calls 10 %, DOM bindings < 1 %; on `marked`, regex 83 %. Against
pinned Chrome on the same pages Boa is ~18× slower than V8 with the JIT off and ~100× slower
than V8 (regex-heavy: 71× / 265×).

**Decision, with the numbers:** embedding first, in this order — LAT7b style-only
`getComputedStyle` (≈ 2.2 s on microsoft; now first in the LAT track after LAT1), S16 (stop
charging forced-layout time to the script budget — Pete's call; gives microsoft ~47 % more
budget), LAT11 incremental forced layout (≈ 1.3 s on github), GC tuning in our Boa fork
(10–15 %), compiled-code cache + precompiled built-ins (repeat loads only). After all of
that, ~3.5 s of pure interpreter time per load remains on github and microsoft and ~8 s on
lyft, and no embedding change closes an 18× interpreter gap. So the engine question is real,
but it comes AFTER the embedding wins, which we need under any engine.
