## C2(d): `position: sticky` sticks

PLAN-z row C2, slice (d). Measured against develop `afa159da`; head `2efc47f6` holds it. #850 has landed, so the diff is this PR alone.

Before this, the engine laid sticky out as static and nothing ever moved it, under a scroller or under the window. The row asks for a box in a scroller to stick to that scroller. There was no window behaviour to correct, so this does both.

### Rule, from Chromium 143.0.7499.4 on the same pages
- A box sticks to its nearest scroller: `overflow` `auto`, `scroll` or `hidden`, used or not. `clip` is not one. With none, it sticks to the window. An absolute box's sticky child answers to its containing block's scroller, not a static one it skips.
- The scrollport is the scroller's padding box less its padding. A percentage inset is of that.
- It stays inside its containing block's content box, keeping its margins. For a direct child of a scroller that box runs across all the scroller can scroll to.
- With both insets on an axis, the far one applies only to a box that fits between them.
- Under a fixed box the window's scroll changes nothing, but the inset still applies.
- Children and absolute descendants go with it. A fixed box inside stays put. A nested sticky box counts its parent's shift.
- `offsetTop` includes the shift. `offsetTop` of a child is from the sticky box, so it does not change.
- It paints as a positioned box, so once stuck it covers an earlier fixed box at the same `z-index`.

### How
- Layout does not move. `LayoutBox::stamp_sticky` gives each sticky box a `rustkit_css::StickyRule` once layout is final, and `StickyRule::shift` is the one calculation. Painter, renderer, hit test and bindings all call it.
- **Under a scroller:** a translate in the list, which is rebuilt when an element scrolls anyway.
- **Under the window:** a new `PushWindowSticky(rule)` command. The renderer works out the translate per frame, so a window scroll does not rebuild the list; a test pins that the list is the same `Arc`.
- **Hit test:** `stamp_sticky_shifts` visits the sticky boxes only, by stored path, so a pointer move does not walk the tree.
- **Script:** rects are worked out live, because script reads them right after a scroll. A sticky box is on the `scroller` chain of what is under it; `scrollChain` skips it because it cannot scroll.

### Changes beyond the row's wording
- **`getBoundingClientRect` of a fixed box and everything in it no longer subtracts the window's scroll.** On develop a fixed box read `-493` at a window scroll of 500 where Chromium reads `7`. New `BoxGeometry::held`. This changes what script reads on any page with a fixed box once scrolled.
- **`elementFromPoint` now reads the window's current scroll.** It read a copy that went stale after `scrollTo` in the same task.
- **An existing test changed:** `fixed_sticky_images_and_iframes_draw_the_same_under_scroll` pinned sticky as static. It now checks the bar at y=22, since the stuck bar covers y<20, and checks that the bar sticks. `c2d_probe5.mjs` shows the same order in Chromium.

### Stacking, added since the first version
A stuck box and a fixed box overlap, so the hit test has to say which is on top.

- **`sticky_is_over`** compares along the stacking-context chain, from where the two paths part: each side is placed by the first context on its way down, then tree order. It read the sticky box's own `z-index`, which was wrong both ways.
- **`z_index_applies`:** `z-index` counts only on a positioned box or a flex or grid item. A static `opacity:.9;z-index:50` wrapper gives the fixed box, as Chromium and develop do.
- **`ComputedStyle::stacks`:** one bit each for `isolation`, `mix-blend-mode`, `perspective`, `transform-style`, `backdrop-filter`, `content-visibility`, `view-transition-name`, and the stacking names in `will-change`. **Only the hit test reads them; none of these paints or lays out by them.** `-webkit-backdrop-filter` makes no context in Chromium 143, so it has no arm.
- **`held`** keys on what gives a fixed box a containing block: transform, filter, `will-change`, `contain`.

**Census:** `backdrop-filter` is still never painted, so it stays a gap: 12 gaps, paint bucket 12. `STACKING_ONLY_ARMS` in `scripts/declaration_census.py` keeps a hit-test-only arm from counting as handled.

### Known gaps
- **Sticky in flex and grid is row C7 and is not tested here.** The rule does not look at the parent's display, but no item is pinned.
- **Not timed:** `stamp_sticky` adds one tree walk per layout, and each `PushWindowSticky` a transform per frame.
- A sticky box does not create a stacking context, where Chromium's does, so a `z-index` inside it is not contained.
- An inline sticky box: Chromium's numbers are in `c2d_probe.mjs`, but no test covers it. The hit test may miss it once moved, if an anonymous line box around it no longer contains the point.
- A `body` that scrolls on its own under an `html` that clips still counts as the window, the same limit as #845.
- An absolute box that escapes a scroller does not count a sticky box outside that scroller as `above`.
- Text selection rects, `Range` rects and diagnostics positions ignore the shift, as they ignore element scroll.
- The window has no horizontal extent (from #850), so sticking to the window across is only tested at scroll x=0 in script. The renderer's arm takes both axes.
- `getBoundingClientRect` leaves transforms out (C10). `a_transform_above_moves_it_after_the_rule` expects Chromium's values less the transform's 100.
- **Percent `opacity` makes no context here** (`opacity:50%`, `99%`): the click goes to the header where Chromium and develop give the fixed box. A regression from this PR, fixed by draft #861, which merges with this head without conflict; its pin passes on that merge.
- `position:relative;z-index:-1` wrapper with the modal -1 before it: header where Chromium has neither. The page hit along chains, out of this PR. Rare.
- `view-transition-name:\41` makes no context; `revert`, `revert-layer`, `default`, `-1`, `a,b` do, where Chromium makes none. Unitless `perspective:100` and `backdrop-filter:foo(1)` make one too. On C12.
- `top_held_or_page` picks among fixed boxes by their own `z-index`, not along the chain. Read from the code, not probed.
