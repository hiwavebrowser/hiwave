## C10 (a): floats and empty blocks keep their margins straight

PLAN-z C10 (a), ledger #474. Batch-testing trial. **Full gates in batch:** suites, campaign and 20-site A/B are left to the batch build. **Expect movers there:** this changes block layout on any page with an empty block that has a margin, and no site was captured for this PR.

**Beyond the row, Atlas to accept or send back:** the float fix alone turned an empty block before a float from right to wrong, because the pending margin it now reads was already wrong. So this also fixes margins through an empty block. It is the wider half of this PR, and it hits pages with no float at all.

### Rule, from Chromium 143.0.7499.4 on the same pages
- **A float starts past the pending margin** of the block before it, and its own margin does not collapse with that one: block bottom at 20, `margin-bottom:30px`, float `margin-top:10px` reads 60. It read 30. The next block still collapses with the pending margin.
- **An empty block's margins collapse through it,** with what is pending before it and whatever comes next: `20 + max(30, 12, 12)` reads 50. It read 62, since the box advanced the flow to its top margin and then its bottom margin was added. Next to a larger margin it was much further off: `two empties` read 120 against 55.
- What stops it: height, `min-height`, border, padding, or a formatting context. An abspos or float child does not, and nor does an empty child block.
- **At the start of a parent,** the margins carry into the parent's own chain and on to the next block's top margin: an empty first child, then a block with `margin-top:40px`, puts the parent at 40.
- **A `clear` that moves the box:** the flow resumes one bottom margin above it, with only that margin pending. Read from Chromium's numbers, on two pages.

### How
- `LayoutBox::collapses_through` decides from style and children. It calls `is_margin_collapsible_through`, which had no caller.
- `MarginCollapseContext::child_collapsed_through` tells the parent to leave its cursor alone.
- `first_child_top_margin_chain` walks past such a box, but not past one with a `clear`.

### Known gaps, none from this PR
Each of these reads wrong on develop too.
- Text before a block in `body`: `x<div style="margin:12px 0"></div>` reads 12 where Chromium reads 30. Cause not traced.

- `<canvas style="display:block">` has no intrinsic size here: the box after it read 62 on develop and reads 50 now, where Chromium reads 212. It wrongly counts as empty, as any such box would.
