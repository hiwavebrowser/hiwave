## Fixed boxes read where they are, wherever the window has scrolled

Atlas's 11-01 07:40 order, off develop `e5e0fd97`. At window scroll 500 the usual centred modal (`position:fixed; left:50%; transform:translateX(-50%)`) read y `-490` where Chromium 143 reads `10`.

### Correction to the order
The order calls this a regression from #852. **It isn't one: every fixed box is wrong, with or without a transform.** A plain `position:fixed` box on develop reads `7 -491` where Chromium reads `7 9`. The cause is that `getBoundingClientRect` and `getClientRects` take the window's scroll off every box. #852's walk didn't add that. It needs one fix either way. #851 carried the same fix, so I took it from there, with the same field name and rule, and #851 now merges this branch.

### Rule, from Chromium 143.0.7499.4 on the same pages
- A fixed box, and everything under it, reads the same rect at any window scroll. That covers transforms on the box or inside it, absolute and flow children, and an element scroller inside it.
- An element's own scroll under a fixed box still moves what it holds.
- A transformed box in the page's flow still goes with the page, and so does an absolute box it holds.

### How
- `BoxGeometry` gains `held`: this box is in a fixed box with no transform above that box.
- The rect read adds the window's scroll back for a held box, so the JS reader's subtraction cancels. It reads `scroll_state`, so a read straight after `scrollTo` in the same task is right.
- `offsetTop` and `offsetLeft` don't change.

### Known gaps
- **`a_transform_holds_fixed_boxes` stays ignored.** Layout still places a fixed box under a transform from the viewport (row C10 item (m)). Such a box isn't `held`, and it reads the same as before.
- **Horizontal window scroll is untested.** The window has no horizontal extent here (`max_scroll_offset.0` is always 0, on the C2 row). The probe's Chromium reading at `scrollTo(30, 500)` is `300 10`, and the engine can't reach that state.
- **Sticky boxes aren't touched**; that is #851.
- **`elementFromPoint` still reads `host.scroll`**, which goes stale after `scrollTo` in the same task. #851 changes that.
- **No real-window run.** The lane has no input grant. This changes script reads, not paint: try a modal's position after a scroll, or a tooltip anchored to a fixed header.
