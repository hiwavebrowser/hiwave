## Percent `opacity`

Batch-testing trial, first PR. **Full gates in batch:** the suites, campaign and 20-site A/B are left to the batch build. Narrow run below.

`opacity` was read by Rust's float parser. `opacity:50%`, which I recall Tailwind v4 writing for `opacity-50` (recalled, not checked), did nothing: no fade, computed `1`, and no stacking context. #851's R1 found this as a click regression. Measured here for computed value and paint, as ordered. Stacking is covered below.

### Rule, from Chromium 143.0.7499.4 on the same pages
- `<number> | <percentage>`, clamped to 0..1 when used. A percentage is a hundredth.
- `calc()` of numbers or of percentages. Adding one to the other is invalid, even `calc(0 + 50%)`.
- `50 %`, `50%%`, `1.`, `inf`, `NaN` and `1px` are dropped, so an earlier valid value stays. The float parser took `1.`, `inf` and `NaN`.
- `opacity:inherit` inherits. It did nothing before, for numbers too.

### Changes
- `rustkit_css::parse_opacity`, used by the `opacity` arm.
- `"opacity"` in `inherit_property`.
- `getComputedStyle` (`dom.rs`): the inline overlay handed back the raw text (`50%`, `2`, `abc`). For `opacity` only, a plain value now reads as its clamped number and anything else reads the last layout's row. **Every other property still has this overlay gap.**

### Not in this PR
- `min()`, `max()`, `clamp()` and the constant `e` inside `calc()` stay unread, so the earlier value stands. Chromium reads them (`min(50%, 75%)` is 0.5).
- `el.style.opacity` still returns what was written; Chromium normalises `50%` to `0.5` and refuses `foo`.
- `keyframes_opacity` has its own parser: it reads `%`, but its float parser still takes `inf` and `NaN`.
